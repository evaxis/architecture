Two distinct histories

Maester Cloud today: history of test results and pass/fail drift. Proposed evidence plane: immutable object-level snapshots and identity-aware differences, including changes that do not change a test's pass/fail state. Never conflate these.

Revenue and cost levers

Revenue: base product entitlement, assessed tenants/assets, historical retention, query volume, enterprise support. Costs: stored GB-month, object operations, query CPU, encryption/KMS operations, egress (where applicable), notifications, support and billing. Set fair-use thresholds and hard customer budgets.

Gate-driven roadmap — not fixed dates

0 · Decisions and constraints

Architecture record + threat model

  • Decide minimal stable evidence format, IDs, completeness and privacy constraints.
  • Explicitly mark unsupported Maester Cloud capabilities and open Pack API questions.
  • Agree compatibility and migration rules before provider implementation.
Exit: reviewed contracts, deployment matrix and threat model.
1 · Baseline integration

Free Pack and offline history prototype

  • Implement Pack adapter aligned to final Maester Module/Import contracts (when published).
  • Validate snapshot structure, deterministic comparisons and local SQLite/files.
  • Emit test outcomes, provider errors and coverage distinctly.
Exit: repeatable offline tests and schema upgrade proof.
2 · Portable evidence layer

Storage + cryptography adapters

  • Versioned envelope encryption with per-customer KEK isolation.
  • At least two adapter tests: local and one object store; exercise export/reimport.
  • Benchmark read/write semantics, integrity, key rotation and disaster recovery.
Exit: verified migration and recovery between backends.
3 · Commercial hosted pilot

One provider, one controlled rollout

  • Deploy authenticated API, quota/usage accounting, billing entitlements and secure operations.
  • Support local vs hosted processing behind operation-level policy.
  • Test real workloads and define customer terms, incident response and support model.
Exit: real unit-economics data and successful tenant-isolation review.
4 · Customer choice

BYOS, second provider and hybrid

  • Implement only when customer demand or resilience justifies it.
  • Enable customer-owned KMS/storage, migration and selective query placement.
  • Preserve portable manifest and entitlement contracts.
Exit: cross-provider tests and audited key migration.
5 · Maester Cloud-native integration

Adopt native evidence API when it exists

  • Map storage and query interfaces to native Maester Cloud service contracts.
  • Negotiate metering, premium entitlement, IP protections and revenue attribution.
  • Offer customer migration without invalidating history or encryption policy.
Exit: verified parity, revenue terms and reversible migration.

Questions to resolve before provider selection

  • Will Maester accept structured Pack evidence or only normal test results?
  • Will its Pack registry support commercial packages or only public manifests?
  • Who is authorised to decrypt under hosted execution, and with what audit trail?
  • How much raw inventory history is really required, and for how long?
  • Are provenance and stable identities sufficient for reliable semantic drift?
  • Does hosted backend processing create UK/EU data residency or contractual requirements?
